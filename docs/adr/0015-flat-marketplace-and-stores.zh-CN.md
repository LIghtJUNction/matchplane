# ADR 0015：平坦的市场和商店

## 地位

公认

## 语境

递归的"平台内平台"术语使普通的商务任务看起来像
基础设施管理。购物者需要一个市场、许多商店、可比较的产品、
和一名助理。商家需要一个稳定的商店身份，无论其目录是由
MatchPlane，作为包交付，或从外部服务连接。

现有的组织、路径、注册、审计记录和 v1 集成合约不能
被安全地重写。它们仍然提供有用的授权和兼容性数据，但它们是
不是产品层次结构。

## 决定

1. 公共产品恰好有两层：一层是市场，一层是商店的扁平目录。
   商店不能包含其他商店。新的注册被附加到规范根
   服务器;调用者不能任意选择父对象。
2. `stores.id`是稳定的商业身份。包注册和联合绑定
   是商店引用的版本化集成记录，而不是商店标识本身。
3. 每个商店都有一个规范的单段公共路径，并且可以保留旧别名。历史
   组织路径保持有效的兼容性范围令牌和审核数据；新的API使用存储
   ID 作为权限，并且永远不会从叶蛞蝓推断所有权。
4. 域仍然是内部目录/模式范围。它们不显示为另一个市场级别。
   报价和市场各方获得 `store_id`；产品外键在一个产品中是唯一的
   商店而不是跨不相关的商店。
5. 公共发现仅读取来自活跃公共商店的活跃报价。服务器可以使用AI来
   选择一组有界的商店，但它会重新读取规范的产品名称、描述、图像、
   返回结果之前，来自 PostgreSQL 的价格、货币、生命周期和存储所有权。
   联系数据、凭据、未发布的优惠、内部租户/域 ID 和远程工具
   输出永远不会成为公共目录字段。
6、客人可以浏览店铺、搜索、比较、使用限界购物辅助。验证
   当用户保存、联系、购买、开设商店或发布产品时开始。买家和卖家
   是一个帐户的操作，而不是帐户类型。
7. 托管、打包和外部集成都项目到同一商店合同。外部的
   检索是建议性的；规范状态、同意、付款、商业条款和审计仍然存在
   市场拥有。
8. 商家收费是明确的商店商业条款：订阅、佣金或披露
   杂交种。赞助曝光必须贴上标签，不能默默地取代有机排名。
9. Better Auth 角色字符串在内部保持稳定。面向用户的副本使用业务术语，例如
   商城负责人、商城运营、店主、店铺运营和店铺成员。

## 结果

- 商城路线做出一次有界商店选择决策和一次规范目录查询；它不
  通过浏览器可见的拓扑更长地递归扇出。
- 旧的递归 API 和路径可以保留适配器，而新的写入和 UI 保持平坦。
- 多个商店可能使用相同的 SKU，而一个商店内的重复项仍然存在冲突。
- 分布式商人保留自己的目录和工具，而不会成为另一个嵌套的商人
  此部署中的市场。
- 删除兼容性树是稍后的迁移，而不是更简单产品的先决条件。
