# MatchPlane 子平台

将遗留子平台包视为市场内的一个商店。商店可能是
托管、打包或外部连接，但它从不包含其他商店。历史
组织路径保持兼容性和授权记录；新产品行为使用
`docs/storefront-contract.md` 描述的稳定存储投影。

## 打包工作流程

1.从经过审查的`matchplane.subplatform.json`开始，将域名内容替换为
   商家提供的舱单数据。不要在根代码中对车辆字段进行硬编码。
2. 验证不可变的 `id`、slug、API 版本、路线、范围、代理阶段/技能/MCP 工具
   名称，以及可选的子平台拥有的检索声明。
3. 注册固定的 Git 提交、存档摘要、托管存储或已审核的外部绑定。这
   服务器始终将其直接附加到市场根目录并投射一个稳定的商店 ID。
4. 仅在所需的构建或外部运行状况检查通过后激活。一家商店有一个规范
   一段路径；旧别名不会创建层次结构。
5. 在稳定的路由/检索信封后面实施存储代理和 MCP 工具。保留向量，
   在商店集成中嵌入模型、提示和类别架构。
6. 保持 UI 干净且可配置域：使用共享聊天和同意流程，应用
   人类艺术温暖不透明的口音处理，并使用苹果风格的即时/可聚焦控制。

使用[references/manifest-and-mount.md](references/manifest-and-mount.md)进行注册，扁平化
安装和检索检查。规范模式位于 `docs/` 下。
